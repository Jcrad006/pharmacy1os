## Scoring definition and limitations

- **C — core counterpart implemented:** source contains a substantive, gated synthetic workflow/data capability, with tests where shown. **C is not TypeScript behavioral equivalence, nor production readiness.**
- **P — partial/different:** related code exists but material original fields, contracts, GUI flow, protocol or proof are missing.
- **M — missing:** no adequate counterpart under this requirement or a release-only capability absent in both prototype baselines.
- Ratings count **one feature each regardless of safety, complexity or business importance**, and must **not** be interpreted as percent implementation, completion, validated release gates or test coverage.

## Most important audit findings

1. **Many October 8 missing items are now code-backed.** Patient email/coverage, DAW/product selection, Rx source/eRx metadata, pharmacist intervention notes, pre-review source correction, original-container packaging, payer masters/rejections/COB correction, locations/stock positions, demand/backorders, historical inventory, inventory exception/discrepancy ledgers, and native Third Party UI now have Python counterparts. Some remain **P**, especially where TypeScript contracts, clinical/legal workflow or UI differ.
2. **Central-client/server gap:** `desktop.py` still instantiates its own **local SQLite** `PharmacyService`; `api.py` has an explicitly local, SQLite-only, opt-in demo entrypoint. There is no deployed authenticated multi-workstation service/client protocol despite passing PostgreSQL concurrency tests against the shared domain layer.
3. **Prisma conversion and endpoint compatibility remain unclosed.** The original 58 Prisma models and 116 Fastify endpoints are **not certified equivalent** or migrated; `py_*` data is separate. The Python desktop cannot be treated as an in-place replacement of the running TypeScript product.
4. **UI and device parity is incomplete.** The native PySide6 interface now includes prescription detail, multi-payer correction and exception worklists, but scanner focus, complete screen-by-screen workflows, PDF/TIFF overlays, production print status, installer/update tooling and complete automated Qt E2E/accessibility test coverage remain unresolved.
5. **External/regulated operations are deliberately not implemented.** Test-only claim events contain no actual payer acceptance, payment or patient responsibility. No production NCPDP, electronic prescribing/fax transport, EPCS, controlled dispensing, card/receipt terminal certification, DSCSA tracing, comprehensive policy/legal review or production identity is present. Requirements absent in the original baseline should be counted as **release gaps, not new Python regressions**.
6. **Correctness proof is narrower than source coverage.** CI passing means the scoped synthetic fixtures passed. It does not prove clinical adequacy, fault recovery, multi-site network operation, true concurrent terminals under outages, signed installers, or TypeScript-equivalent historical data.

## Prioritized closure plan

**P0: clinical/data integrity before declaring parity**
- Build a deterministic, recoverable **58-model Prisma→SQLAlchemy field crosswalk and conversion harness**, with matched source IDs, cardinality, constraints, status history, audit, signed documents, rollback and independent reference checks on disposable records.
- Implement deterministic **116-route old/new compatibility decisions** (exact adapter or deliberate breaking API version), including error semantics, role/site checks, idempotency, immutable provenance, negative scenarios and data contracts.
- Finish especially consequential incomplete workflows: biologic interchange communication, specialized/controlled handling (remain fail closed), pricing/patient share semantics, manufacturer master and inventory transfer custody. Maintain separate regulatory/real-payer release gates.

**P1: ship a real networked developer prototype**
- Separate PySide6 client from its in-process SQLite domain and provide a guarded **central Python service backed by PostgreSQL**. Centralize Rx/document/payer/inventory transactions, authenticated roles and concurrency/failure handling. Do **not** expose the existing demo-header API to a shared network.
- Implement cohesive native dialogs for advanced inventory, catalog, clinical, Third Party, POS and document review, with refresh/stale-selection handling and source-matched keyboard/scanner behavior.
- Add Qt end-to-end GUI/device-mock flows, explicit printer outcome reconciliation and native installer/update/signing rehearsal on supported platforms.

**P2: exit criteria and release validation**
- Run matching original/Python golden fixtures for every implemented original feature; ensure no unexplained `P`/`M` without documented conscious de-scope.
- Test PostgreSQL cross-process competing actions, reconnect/crash recovery, power/network outages, migrations, restore/recovery and longitudinal audit.
- Require pharmacist-led safety review and applicable legal/security/compliance engineering before real PHI, dispensing, external claims or devices. **Do not merge draft PR #43 as a production cutover.**

**58/138 requirements currently have a source-confirmed core synthetic Python counterpart, 61/138 remain materially partial, and 19/138 have no adequate counterpart.** The count tracks *presence*, not feature parity certified. A replacement decision still requires field/model, endpoint, end-to-end desktop, cross-language and recovery testing. The current Python rewrite is a substantial but incomplete experimental pharmacy information system.
